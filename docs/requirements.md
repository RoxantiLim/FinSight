# 需求与范围

## 1. 项目目标

FinSight Agent 的目标是证明：模型能够围绕用户的财务目标，自主选择结构化数据工具，读取结果后继续调查，并生成有数据依据、金额自洽且受写操作确认机制保护的计划。

项目的主要受众是 AI Agent / LLM 应用开发岗位的面试官、项目评审者和未来维护者。当前优先级是尽快完成可稳定演示、能够讲清设计取舍的面试版，而不是补齐通用记账产品的全部功能。

## 2. 核心用户故事

### US-01 体验演示数据

作为访客，我可以一键加载内置模拟账单，无需提供真实财务数据即可体验完整功能。

验收条件：

- 数据生成使用固定种子；
- 每次重建得到相同的业务事实；
- 数据覆盖最近 6 个完整月份，共 300～500 条交易；
- 包含工资、房租、餐饮、交通、购物、订阅、退款、转账和异常消费。

### US-02 导入异构账单

作为用户，我可以上传模拟的微信或支付宝 CSV 账单，系统自动识别来源、校验字段、统一格式并导入。

验收条件：

- 微信和支付宝分别使用独立适配器；
- 同一文件重复导入不会产生重复交易；
- 错误报告包含行号和原因，不记录完整敏感交易；
- 退款、转账和红包不会默认计入普通消费。

### US-03 查看确定性统计

作为用户，我可以查看月度收入、支出、结余、分类占比和趋势。

验收条件：

- 金额由 SQL 或确定性 Python 代码计算；
- 金额使用分为存储单位，展示时转换为元；
- 每个指标明确是否包含退款、转账和一次性支出；
- 同一数据和同一参数始终返回相同结果。

### US-04 自然语言分析

作为用户，我可以提出开放式财务问题，Agent 根据问题动态选择一个或多个工具。

验收条件：

- 工具调用顺序不由固定业务流水线写死；
- Agent 能读取一次工具结果并决定继续查询或结束；
- 界面展示工具名称、参数摘要、状态、耗时和结果摘要；
- 最终结论引用其使用的数据区间和关键金额。

### US-05 生成储蓄计划

作为用户，我可以输入下月储蓄目标，获得基于最近三个月数据的计划。

验收条件：

- 计算当前平均结余和目标缺口；
- 区分固定、可变、周期性和一次性支出；
- 建议削减金额之和覆盖储蓄缺口，或明确说明目标不可行；
- 每项建议说明证据和影响；
- 模型不得自行编造交易或金额。

### US-06 确认后保存预算

作为用户，我可以审阅 Agent 提议的预算，并明确确认或拒绝保存。

验收条件：

- 提议阶段不写入正式预算表；
- 系统只在当前用户明确确认后开放写工具；
- 确认请求包含待写入内容、过期时间和不可重复使用的令牌；
- 拒绝、超时或内容变化均不执行写入；
- 保存后返回预算编号和实际写入内容。

### US-07 分类纠错与规则记忆（面试版完成后）

作为用户，我可以修改交易分类，并选择是否为相同商户建立规则。

验收条件：

- 修改分类前需要确认；
- 规则只影响当前用户；
- 后续导入优先应用用户规则；
- 所有修改保留来源和时间，便于追踪。

## 3. 功能范围

### 面试版必须完成

- 固定、可复现、带标准答案的模拟数据；
- 微信与支付宝 CSV 适配器；
- 统一交易模型、去重和导入报告；
- 月度统计、期间对比、分类分解、周期支出和异常交易工具；
- 模型原生 Tool Calling 的多轮 Agent 循环；
- 储蓄缺口计算与预算模拟；
- 工具调用轨迹；
- 预算保存的用户确认；
- 自动化测试、固定评测集和演示脚本；
- 本地可运行的 Web 界面。

### 核心演示完成后再做

- 单笔交易分类纠错；
- 为商户创建分类规则；
- LLM 兜底分类与置信度审核；
- 更多真实账单版本兼容；
- 完整的隐私设置页面；
- PostgreSQL、Docker 和公开部署。

### 明确不做

- 登录、爬取或自动同步微信和支付宝账户；
- 投资推荐、股票交易、借贷决策、税务或法律建议；
- 多用户生产级身份认证与权限系统；
- 银行卡或支付账户连接；
- 向量数据库和 RAG；
- Redis、消息队列、微服务或 Kubernetes；
- 多 Agent 协作；
- 模型微调；
- 移动端原生应用；
- 高级会计功能或资产负债表。

第一版只承诺兼容项目内置、可复现的微信与支付宝代表性样例。真实用户账单兼容属于增量能力，不能阻塞核心 Agent 演示。

## 4. 业务口径

- `income`：工资、退款之外的真实资金流入；
- `expense`：用于消费统计的真实支出；
- `refund`：单独记录，并在净支出中抵扣对应分类；
- `transfer`：账户间或个人间转账，默认不计入收入或消费；
- `red_packet`：单独标记，默认不参与常规消费趋势；
- `fixed`：金额和周期较稳定、短期难以削减的支出；
- `recurring`：按近似周期重复出现的支出，不一定都是固定支出；
- `one_off`：不应外推到未来月份的一次性支出；
- `balance`：纳入口径的收入减去净支出。

所有工具必须在返回值中携带统计口径，避免同一个“支出”在不同页面含义不同。

## 5. 非功能需求

### 正确性

- 金额不使用二进制浮点数持久化；
- 关键统计提供单元测试和手工可核对样例；
- Agent 输出中的关键金额必须能追溯到工具结果；
- 写工具具备幂等性。

### 隐私与安全

- 默认日志不包含完整商户、备注、订单号或原始文件内容；
- 真实账单路径和本地数据库加入 `.gitignore`；
- 上传文件限制类型和大小；
- 工具参数经过服务端校验；
- Agent 无法绕过确认令牌直接执行写操作。

### 可观察性

- 每次 Agent 运行具有唯一 ID；
- 记录工具名称、参数摘要、执行状态、耗时和结果摘要；
- 不保存或展示模型私有推理过程；
- 失败时向用户给出可操作的错误信息。

### 可维护性

- 来源适配、领域模型、分析工具、Agent 编排和 UI 分层；
- 工具拥有稳定的输入输出 schema；
- 各里程碑均提供运行命令和验收说明；
- 合理默认项由代码配置，不散落在提示词中。

### 性能

- 在 500 条演示交易上，单个分析工具本地执行目标低于 500 ms；
- 不含模型等待时间的普通接口目标低于 1 s；
- 一次 Agent 运行限制最大工具调用次数和总超时，防止无限循环。

## 6. 成功标准

MVP 完成时必须同时满足：

1. 新用户可以在 5 分钟内启动并加载演示数据；
2. 核心储蓄问题产生至少两次由模型决定的有效工具调用；
3. 最终计划的关键金额与标准答案一致，削减合计自洽；
4. 至少三个不同问题产生不同的合理工具路径；
5. 未确认时预算表保持不变，确认后只写入一次；
6. 核心测试和固定评测集可以重复运行；
7. README、演示脚本和架构说明足以支持 5～8 分钟面试演示。
