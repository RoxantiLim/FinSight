# 开发里程碑

## 工作方式

每次只实现一个里程碑。开始前重述本阶段目标和验收标准；完成后实际运行验证，并说明修改文件、数据流、运行命令、预期结果和必须理解的三个知识点。上一阶段未验收前不进入下一阶段。

预计总周期为 3～4 周，时间仅用于控制范围，不作为完成承诺。

## M0：项目规划（已完成）

目标：冻结 MVP 的产品范围、架构边界、数据模型、Agent 定义、开发顺序和评测方式。

产出：

- `README.md`；
- `docs/requirements.md`；
- `docs/architecture.md`；
- `docs/data-model.md`；
- `docs/agent-design.md`；
- `docs/milestones.md`；
- `docs/evaluation.md`。

验收：

- 核心场景和非目标没有冲突；
- 可以明确解释模型、工具和用户各自负责什么；
- 每个后续里程碑都能独立运行和验收；
- 文档没有声称尚未实现的功能已经可用。

状态：已于 2026-09-23 收敛为面试版范围。

## M1：可复现数据与账单导入（已完成）

目标：建立不依赖大模型的数据基础。

实现：

- Python 项目骨架、配置和测试框架；
- SQLite + SQLAlchemy 表结构和迁移/初始化方式；
- 固定种子的 6 个月模拟交易生成器；
- 同一事实数据导出为微信、支付宝两种模拟 CSV；
- 来源识别、适配、归一化、校验和去重；
- `demo_ground_truth.json`；
- CLI 或最小 API 完成重建和导入。

验收命令应证明：

- 第一次导入新增 300～500 条；
- 第二次导入新增 0 条并报告重复；
- 两种来源被正确归一化；
- 金额、退款、转账和异常样例与 ground truth 一致；
- 导入测试通过。

本阶段不调用任何模型。

状态：已于 2026-09-23 完成。固定种子生成 357 条交易，首次导入新增 357 条，重复导入新增 0 条；Pytest 3 项和 Ruff 检查均通过。下一阶段为 M2。

执行约束：

- 参考 `Bean-Sieve` 与 `china_bean_importers` 的字段映射和测试思路；
- 不引入 Beancount 账本能力；
- 先用项目自己的最小 `WechatAdapter`、`AlipayAdapter` 接口；
- 若第三方解析器不能在短时间内稳定转换到统一模型，立即改为实现两个最小适配器，不继续扩展兼容范围；
- 第一版只保证项目内置代表性样例通过。

## M2：确定性分析工具（已完成）

目标：把所有需要精确计算的能力实现为可单独测试的工具。

实现：

- `search_transactions`；
- `get_monthly_summary`；
- `compare_periods`；
- `get_category_breakdown`；
- `find_recurring_expenses`；
- `find_abnormal_transactions`；
- `calculate_saving_gap`；
- `simulate_budget`；
- Pydantic 输入输出 schema；
- 最小 FastAPI 只读接口或 CLI 调试入口。

验收：

- 每个工具可以脱离 Agent 独立调用；
- 核心金额与 `demo_ground_truth.json` 一致；
- 日期边界、退款、转账、空数据和非法参数有测试；
- `simulate_budget` 能判定计划是否覆盖缺口；
- 工具不返回不必要的敏感字段。

状态：已于 2026-09-26 完成。8 个工具均可通过统一注册表和 CLI 独立调用；核心金额与 ground truth 一致；完整测试 11 项、Ruff 检查通过。下一阶段为 M3。

## M3：模型驱动的 Agent 工具循环

目标：完成区别于固定 workflow 的核心 Agent 能力。

实现：

- DeepSeek Responses API 接入；
- 只读工具 schema 注册；
- 多轮 function calling 执行循环；
- 参数校验、工具错误返回、重复调用保护、调用上限和超时；
- 命令行或 API 对话入口；
- Agent 运行与工具调用轨迹；
- 记录模型和提示词版本。

验收：

- 核心储蓄问题触发多次有效工具调用；
- “异常消费”“周期支出”“期间比较”产生不同工具路径；
- 模型根据中间结果继续查询，而非代码固定执行全部工具；
- 最终金额来自工具结果并通过预算模拟；
- 模型调用失败时给出可理解错误，不产生无限循环；
- 固定 Agent 评测集可以运行。

## M4：Human-in-the-loop 写操作

目标：让 Agent 能提出操作，同时保证未经确认不会改变数据。

实现：

- `pending_actions` 状态机；
- 创建预算提议、确认、拒绝、过期和幂等执行；
- `create_budget_plan`；
- 审计字段和权限校验。

验收：

- 只提出计划时预算表不变；
- 拒绝或过期动作不能执行；
- payload 被修改后确认失败；
- 有效确认只写入一次；
- 绕过 Agent 直接请求写接口也必须通过确认校验。

## M5：可演示 Web 界面

目标：把已经验证的后端能力组合成完整用户体验。

实现：

- Streamlit 首页；
- “体验演示数据”和“导入我的账单”入口；
- 月度趋势、分类占比和结余概览；
- Agent 聊天区和预设问题；
- 可折叠工具轨迹；
- 预算提议确认/拒绝界面；
- 导入错误与空数据状态。

验收：

- 新用户从空数据库到核心问答不超过 5 分钟；
- 页面不显示密钥、原始订单号或敏感日志；
- 核心场景可从 UI 完整走通；
- 页面刷新后已确认预算仍存在；
- 不可用状态有明确反馈。

## M6：评测、可靠性与作品集交付

目标：用可重复证据证明项目有效，并完成面试演示材料。

实现：

- 固定评测数据集与自动 grader；
- 导入、工具、Agent 和确认机制的端到端测试；
- 失败样例与回归测试；
- 隐私检查和 `.gitignore`；
- `.env.example` 和完整本地启动命令；
- Docker 化（仅在不影响进度时）；
- 5～8 分钟演示脚本；
- README 截图、架构说明、设计取舍和已知限制；
- 简历项目描述草稿。

验收：

- 新环境按 README 可以启动；
- 必要测试和评测命令通过；
- 评测报告包含工具路径、事实正确率和写操作安全结果；
- 核心演示可连续重复至少三次；
- 可以在 2 分钟内解释“为什么这是 Agent”；
- 可以说明三个主动舍弃的技术及原因。

## 后续可选项

只有 MVP 完成并有实际证据后再考虑：

- PostgreSQL 和正式部署；
- React/Next.js 前端；
- 更真实的账单格式兼容；
- 分类纠错与商户规则记忆；
- 跨会话可恢复的复杂 Agent 状态；
- 多币种和多账户；
- 更完善的身份认证。

这些项目不计入 MVP 完成条件。
