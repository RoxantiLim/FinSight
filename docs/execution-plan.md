# 面试版执行计划

## 1. 最终目标

当前目标不是完成一个通用记账产品，而是尽快交付一条可以稳定演示、能够量化验收、面试时可以解释的 Agent 链路。

面试演示必须完成：

1. 一键加载固定演示数据；
2. 用户提出“我下个月想存下 2,000 元”；
3. 模型自主调用多个分析工具；
4. 界面展示不同工具的调用轨迹；
5. 工具计算最近三个月结余、储蓄缺口和可削减支出；
6. Agent 调用预算模拟验证方案；
7. 最终建议的金额能够自洽；
8. 用户确认后才保存预算；
9. 固定评测证明金额和权限边界正确。

只要这条链路稳定，面试版即成立。

## 2. 已冻结的技术路线

| 模块 | 决策 | 当前不做 |
|---|---|---|
| 语言 | Python 3.12 | 多语言服务 |
| 依赖管理 | `uv` + `pyproject.toml` | 多套 requirements 文件 |
| 数据库 | SQLite + SQLAlchemy | PostgreSQL、Redis |
| API | FastAPI | 微服务、消息队列 |
| UI | Streamlit | React/Vue 移动端 |
| Agent | DeepSeek Responses API Tool Calling 的单 Agent 循环 | 多 Agent、复杂固定图 |
| 测试 | Pytest | 大型测试平台 |
| 数据 | 固定生成数据 + 两种代表性账单样例 | 自动抓取支付账户 |

除非出现无法继续的技术阻塞，执行期间不更换技术栈。

## 3. 借鉴策略

### 账单解析

参考：`Bean-Sieve`、`china_bean_importers`。

借鉴内容：微信与支付宝文件头定位、编码和空白处理、字段映射、收支方向、退款/转账/红包判断、订单号、去重字段和测试案例。

执行选择：项目内部定义自己的统一 `TransactionInput` 和两个最小 Adapter。第三方项目不成为核心运行时依赖，除非试验能证明接入比自行实现明显更简单。

### 项目分层与状态管理

参考：`financial-inteligence-agent`。

借鉴 API、service、repository、agent、UI 分层，演示数据脚本，运行记录与 human-in-the-loop 状态。不借鉴多 Graph、OCR、汇率、n8n、MCP、图像账单和复杂部署。

### Agent 工具组织

参考：`Open Accountant / Wilson`。

借鉴工具注册表、稳定输入输出 schema、Agent 与确定性服务的边界，以及异常交易和周期支出工具的职责划分。不引入其 TypeScript/Bun 技术栈。

### 页面布局

参考：`xiaoyaoprivatebill` 与 `AJ/FinSight` 的演示数据入口、上传区、统计卡片、趋势图、分类图、聊天区和预算确认卡片。全部使用 Streamlit 重新实现。

## 4. 自己实现的核心贡献

- 面向储蓄目标的财务工具契约；
- 确定性统计与预算计算；
- 模型驱动的连续 Tool Calling 循环；
- 根据中间结果继续调查的行为；
- 面向用户的工具轨迹；
- 预算保存的两阶段确认协议；
- 固定 ground truth 和 Agent 评测；
- 核心演示问题的端到端链路。

这些是简历和面试讲解的重点。

## 5. 执行顺序

```text
M1 数据基础
  -> M2 确定性分析工具
  -> M3 动态 Agent 循环
  -> M4 预算确认保存
  -> M5 Streamlit 演示界面
  -> M6 评测、演示脚本和简历材料
```

每个阶段验收后再进入下一个阶段。UI 不能先于工具和 Agent 正确性。

## 6. M1 立即执行清单

状态：已于 2026-09-23 全部实现并通过验收。实际证据见根目录 `README.md` 的“M1 验收结果”。

### 6.1 项目骨架

- 初始化 Git 仓库，并将当前规划文档作为第一个可追踪基线；
- 创建 `pyproject.toml`；
- 创建 `app/`、`scripts/`、`data/demo/`、`tests/`；
- 配置 `pytest`、`ruff` 和基础日志；
- 创建 `.env.example` 与 `.gitignore`。

### 6.2 最小数据模型

M1 只实现 `import_batches` 和 `transactions`。预算、Agent 运行和确认表在对应里程碑再加入。

### 6.3 演示数据

- 使用固定随机种子；
- 生成最近 6 个完整月份、300～500 条交易；
- 包含工资、房租、餐饮、交通、购物、订阅、退款、转账和一次性异常支出；
- 导出统一数据、微信样例和支付宝样例；
- 生成 `demo_ground_truth.json`。

### 6.4 导入能力

- 定义 `BaseBillAdapter`；
- 实现 `WechatAdapter`；
- 实现 `AlipayAdapter`；
- 统一转换为 `TransactionInput`；
- 使用订单号或规范化内容哈希去重；
- 返回新增、重复、忽略和失败数量。

### 6.5 M1 验收

M1 只有在以下证据全部出现后才能完成：

1. 演示数据可重复生成；
2. 数据量在 300～500 条；
3. 微信和支付宝样例均可导入；
4. 第一次导入产生交易；
5. 第二次导入新增 0 条；
6. 退款和转账口径符合 ground truth；
7. 导入相关测试通过；
8. README 出现经过实际验证的安装与运行命令。

M1 不接入模型、不做聊天、不做图表。

## 7. 后续阶段的最小交付

- **M2**：实现 8 个可独立调用和测试的分析工具，不调用模型。
- **M3**：实现单 Agent 多轮工具调用，先通过 CLI 或 API 证明动态路径。
- **M4**：只实现预算计划的待确认、确认、拒绝、过期和幂等保存。
- **M5**：只实现核心演示需要的 Streamlit 页面。
- **M6**：补齐固定评测、回归测试、演示脚本、截图和简历描述。

## 8. 范围控制规则

- 新功能如果不能直接增强核心演示，则移到后续列表；
- 第三方项目如果接入成本超过自行实现最小版本，则停止接入；
- Agent 之前必须先有可靠工具；
- UI 之前必须先有可验证的 Agent API；
- 不为技术栈丰富度增加组件；
- 不在一个里程碑中顺手实现下一个里程碑；
- 格式兼容问题优先保证内置样例，不无限兼容真实账单。
